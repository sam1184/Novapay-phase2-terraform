01

A backup you've never restored isn't a backup — it's a hope.

// plenty of teams have backups · far fewer have ever proven they work
Risk Silent backup gaps Default Untested "backups" Fix A real, repeatable drill Tool Velero + EBS CSI
Scenario
For NovaPay the question is concrete: someone fat-fingers kubectl delete namespace novapay-prod, or a Region has a bad day, or a migration script wipes the ledger table. How fast do you get back — and did you actually get everything back?

The trap is this: backing up the Kubernetes manifests but not the persistent volume data. Your Deployments and Services come back instantly when you restore — the app looks "running" again within seconds. But the database volume is empty. NovaPay's transaction ledger, the thing that actually matters, is gone, and nothing in the dashboard tells you that until a customer asks where their payment went.

This module is a real DR drill, not a slideshow. A stateful workload writes real transaction records to a real EBS volume. Velero backs the whole namespace — including that volume's data — up to S3. We delete the namespace for real. We restore it. We checksum the data before and after. If the checksums match, the restore is real. If they don't, you just found out in a lab instead of in production.

Architecture
Production Reality
It's rarely a dramatic failure. A team has Velero, or a snapshot tool, or a backup cron job running for months. Dashboards are green. Then a real incident hits — a bad migration, an accidental delete, a Region issue — and someone restores for the first time. The objects come back. The pods go Running. Everyone exhales.

Then someone queries the database and it's empty, or three weeks stale, or the volume never actually got attached to the snapshot job. The gap wasn't in the tooling. It was in never having run the restore path until the day it was the only path. Test restores on a schedule. A backup you've never restored is a hope, not a plan.
02

Velero: the standard tool for Kubernetes backup, restore, and DR.

// open-source · runs inside your cluster · backs up objects and volumes
Type K8s-native backup Stores to S3 (any bucket) Volume engine node-agent (Kopia) Auth Pod Identity, no keys
Concept
CONCEPT

Velero does two jobs, not one

// THE REAL-WORLD ANALOGY
Think of a Kubernetes namespace as a filing cabinet (the objects — Deployments, Services, ConfigMaps, the PVC paperwork) sitting next to a safe (the actual EBS volume bolted to a node, holding the real bytes). Backing up only the filing cabinet photographs the labels on the safe, not what's inside it. Velero is built to do both: photograph every piece of paperwork in the API server, and — when you ask it to — open the safe and copy out the contents too.

Concretely, on every velero backup create, two things happen in parallel:

  1. The Velero server asks the Kubernetes API for every resource matching your selector (a namespace, by label, or the whole cluster) and writes each one as a file, uploaded to S3.
  2. The node-agent DaemonSet (using the embedded Kopia engine) finds any PVC mounted by those pods, walks the filesystem on the volume, and copies the actual files to the same S3 backup — this is filesystem-level backup, not an EBS snapshot.
Architecture
In This Lab

In this lab we set --default-volumes-to-fs-backup on the Velero install, so every PVC's data is backed up at the filesystem level by default — no per-pod annotations to remember, no opt-in step that's easy to skip. Restore is the mirror image: Velero reads the backup from S3, recreates the Kubernetes objects through the API server, and the node-agent rehydrates the volume by copying the files back into a freshly provisioned EBS volume before the pod is allowed to start.

03

RTO and RPO — the two numbers that matter.

// every DR conversation comes down to these · learn them once
RTO Recovery Time RPO Recovery Point This lab Measures RTO live Part G Sets the RPO
Definitions
TermQuestion it answersWhat controls it
RTORecovery Time Objective — how long until we're back up?How fast your restore runs, and how automated it is. Manual, multi-step restores blow your RTO. A scripted, one-command restore protects it.
RPORecovery Point Objective — how much data can we afford to lose?How often you take backups. Hourly backups mean you can lose, at worst, up to an hour of writes. RPO is a backup-frequency decision, not a restore-time decision.
// HOW THIS LAB MAPS TO BOTH The lab measures RTO live — it times the restore, from velero restore create until the ledger workload is Ready, and prints the number in seconds. It makes RPO explicit in Part G, by creating an hourly backup schedule — which means your worst-case data loss is bounded at one hour, not "whenever someone last ran a backup manually."
04

What gets backed up: objects vs. volume data.

// the distinction that separates a real DR setup from a fake one
Layer 1 K8s objects Layer 2 Volume bytes Captured by node-agent Engine Kopia (fs-backup)
Two Layers
LayerExample in NovaPayHow Velero captures it
K8s objectspayment-service Deployment, Services, the novapay-settings ConfigMap, the PVC definitionAPI server query → written as files in S3. Fast — seconds, regardless of data size.
Persistent volume datathe ledger volume's transaction records — every line in /data/ledger.txtnode-agent (Kopia) copies the files inside the mounted volume → S3. Scales with data size.

A backup that only captures the first layer will restore a namespace that looks perfect and contains nothing. The whole point of Module 11 is making the second layer impossible to forget — by checksumming it, every single run.

05

How Velero authenticates: Pod Identity, no keys.

// no IAM user · no access key · no secret mounted anywhere
Old way Static IAM keys This lab EKS Pod Identity Scope One S3 bucket only Flag --no-secret
Concept
CONCEPT

Why static keys are the wrong default

Velero needs AWS permissions to write to the S3 bucket and take EBS snapshots. The old way: create an IAM user, generate an access key, and mount it into the Velero pod as a Kubernetes Secret. That key never expires on its own, it sits in etcd, and anyone with read access to the velero namespace can read it out and use it from a laptop on the other side of the world.

This lab uses EKS Pod Identity instead. Terraform creates an IAM role scoped to exactly one S3 bucket (plus the EBS snapshot actions Velero needs), and associates that role with the velero service account. The EKS Pod Identity Agent injects short-lived, auto-rotating credentials into the pod at runtime — there is no key to leak, because there is no key.

Architecture
Scoped IAM
The Velero IAM role created by main.tf can only touch the backup bucket — nothing else in the account: 
# aws_iam_role_policy.velero — scoped to one bucket + EBS snapshots
s3:GetObject / PutObject / DeleteObject     on  novapay-dr-velero-<account>/*
s3:ListBucket / GetBucketLocation           on  the bucket itself
ec2:CreateSnapshot / DeleteSnapshot / ...     for EBS snapshot support
06

The drill: back up, destroy, restore, verify.

// the whole point of the module · seven parts · run by module-11-demo.sh
Script module-11-demo.sh Parts A through G Checks 12 automated Expect PASSED:12 FAILED:0
Part A
PART A

Prerequisites

~10 sec

Before trusting any backup, confirm the backup system itself is healthy: Velero's server is Running, the node-agent (which backs up volume data) is Running on every node, the S3 BackupStorageLocation is Available, and the ledger PVC is actually Bound to a real EBS volume.

# Velero server + node-agent both Running, BackupStorageLocation Available
kubectl get pods -n velero
kubectl get backupstoragelocation default -n velero -o jsonpath='{.status.phase}'

# The stateful ledger volume must be Bound before we write data to it
kubectl get pvc ledger-data -n novapay-prod
Part B
PART B

Write real data

~5 sec

We write 500 real transaction records to the ledger volume, then record two things: the exact line count, and an md5 checksum of the file. This is our recovery point — everything we compare against after the restore. Anything written after this moment is, by definition, outside this backup's RPO.

# Write 500 transaction records, then checksum the file
kubectl exec deploy/ledger -n novapay-prod -- sh -c 'i=1; while [ $i -le 500 ]; do
  echo "TXN-$i,amount=$((i*7)),account=ACC$((i%50))" >> /data/ledger.txt
  i=$((i+1))
done; sync'

ORIG_COUNT=$(kubectl exec deploy/ledger -n novapay-prod -- wc -l < /data/ledger.txt)
ORIG_MD5=$(kubectl exec deploy/ledger -n novapay-prod -- md5sum /data/ledger.txt)
Part C
PART C

Back up

~30-60 sec

One command backs up the entire novapay-prod namespace — every Deployment, Service, and ConfigMap, plus (because of --default-volumes-to-fs-backup on install) the ledger volume's file contents. We confirm the backup phase is Completed and that a PodVolumeBackup exists for the ledger — proof the data layer, not just the manifests, made it to S3.

# Back up the whole namespace, manifests + volume data, and wait for it to finish
velero backup create novapay-dr-$(date +%Y%m%d%H%M%S) \
  --include-namespaces novapay-prod \
  --wait

# Confirm the ledger volume's data was actually captured, not just the PVC object
kubectl get podvolumebackups -n velero \
  -l velero.io/backup-name=<backup-name>
Part D
PART D

Disaster

~10 sec + propagation

We delete the entire namespace. This removes the pods, the Services, the ConfigMap, the PVC — and because the gp3 StorageClass's reclaim policy is Delete, the real underlying EBS volume and every byte on it are destroyed along with it. This is a true loss, not a pause. There is nothing left to recover from except the S3 backup.

# For real. Pods, Services, the ConfigMap, the PVC — and the EBS volume — all gone.
kubectl delete namespace novapay-prod --wait=true --timeout=180s

# Confirm there is genuinely nothing left
kubectl get ns novapay-prod
Part E
PART E

Restore (measure RTO)

timed live

One command recreates every Kubernetes object and rehydrates the ledger volume from the S3 backup. We start a timer the instant the restore is requested and stop it once the ledger workload reports Ready — that elapsed time is your RTO, measured, not estimated from a runbook nobody has actually executed.

# Time the restore, end to end
RTO_START=$(date +%s)

velero restore create novapay-restore-$(date +%Y%m%d%H%M%S) \
  --from-backup <backup-name> \
  --wait

kubectl rollout status deploy/ledger -n novapay-prod --timeout=180s
RTO=$(( $(date +%s) - RTO_START ))
echo "RTO: ${RTO}s"
Part F
PART F

Verify — the real proof

~10 sec

Namespace back, deployments back, the PVC re-bound to a fresh EBS volume, the ConfigMap restored — that's the easy half, and it's the half a manifests-only backup would also pass. The real check: read the ledger file back out, take its line count and md5 again, and diff against what Part B recorded. Equal checksums mean the restored volume is byte-for-byte the data we backed up. That's zero data loss, proven, not assumed.

# The real DR proof — compare before/after checksums
NEW_COUNT=$(kubectl exec deploy/ledger -n novapay-prod -- wc -l < /data/ledger.txt)
NEW_MD5=$(kubectl exec deploy/ledger -n novapay-prod -- md5sum /data/ledger.txt)

# PASS condition: NEW_COUNT == ORIG_COUNT  &&  NEW_MD5 == ORIG_MD5
echo "Before: count=$ORIG_COUNT md5=$ORIG_MD5"
echo "After:  count=$NEW_COUNT  md5=$NEW_MD5"
Result

Expected ending: PASSED: 12 FAILED: 0

  • A measured RTO, in seconds, not a number copied from a slide deck
  • Identical before/after md5 checksums — the persistent volume data survived the round trip
  • The full namespace — manifests and the real ledger data — recovered from S3 with zero data loss
07

Schedules: turning a one-off backup into real DR.

// DR is automatic, regular, and off-site · not a manual command someone remembers
Object Velero Schedule Cron 0 * * * * (hourly) Retention 7 days (TTL) Defines Your RPO
Part G.1
PART G.1

Create a recurring backup schedule

A one-off backup, run once by a human, isn't disaster recovery — it's a snapshot of one moment that gets staler every day nobody re-runs it. A Schedule turns the same backup logic into a standing policy. The cron expression here is your RPO dial: hourly means at most an hour of data loss in the worst case; tighten it for less potential loss, loosen it to save on storage and API calls.

# Hourly backups, 7-day retention — your RPO is now 1 hour, not "whenever"
velero schedule create novapay-hourly \
  --schedule="0 * * * *" \
  --include-namespaces novapay-prod \
  --ttl 168h0m0s
08

Cross-region and cross-cluster DR — the production pattern.

// same backup/restore mechanic · only the target cluster changes
This lab Same cluster Production Different Region Bucket S3 replication Cutover DNS / Global Accelerator
Why It Differs

This lab restores into the same cluster on purpose — it keeps the drill cheap and fast to run repeatedly. Real production DR restores into a different cluster, usually in another AWS Region entirely, so that a Region-wide event doesn't take out your backups along with your primary. The mechanic — back up, lose everything, restore, verify checksums — is identical. Only the target cluster changes.

Architecture
The Four Steps
  1. Replicate the S3 backup bucket to the DR Region — S3 Cross-Region Replication, or simply a bucket the DR cluster can read.
  2. Stand up a DR EKS cluster there, and install Velero pointed at the replicated backups.
  3. Run velero restore create --from-backup <name> in the DR cluster — the exact command from Part E.
  4. Repoint DNS or your Global Accelerator at the DR cluster.

The backup/restore mechanic you just ran end-to-end in Part 6 is the core of every one of these four steps. Same backup, different cluster.

09

Gotchas and production notes.

// the failure modes that make a backup look fine when it isn't
Most common Manifests-only Silent failure node-agent down Discipline Test restores At scale Tighten DB RPO
Watch For

Common failure modes in production DR setups

  • Manifests without volume data is the classic mistake. Always confirm a PodVolumeBackup (or snapshot) completed, not just the parent backup object. No PV data captured, and you won't notice until the restore comes back empty — Part C exists to catch this every single run.
  • The node-agent must be Running. For filesystem backup, no node-agent means no PV data captured, silently. Check it in Part A, every time, before you trust anything downstream.
  • Velero is for the cluster + config + smaller volumes. For the actual transactional database, prefer database-native DR (RDS/Aurora automated backups and cross-Region read replicas). Use Velero for the application layer around it, not as a substitute for a database engine's own replication.
  • Test restores on a schedule, not just at incident time. A backup you've never restored is a hope, not a plan. Run this drill regularly — it's built to be re-run, not a one-time exercise.
  • RPO for money is not your backup interval by accident. gp3 here is set to Delete reclaim policy, so deleting the namespace really destroys the volume — which is what makes the drill honest. Know your StorageClass's reclaim policy; your payment data should have a much tighter RPO via the database tier than an hourly Velero schedule alone provides.

Before You Run

Always tear down when you're done

  • ~$0.35/hour while running — EKS control plane, 2 worker nodes, a NAT Gateway, a small S3 bucket, and one EBS volume.
  • teardown.sh deletes the Velero schedule and all backups, removes the namespace and Velero install (releasing the EBS volume), then runs terraform destroy.
  • The S3 bucket has force_destroy = true set in Terraform specifically so destroy can empty and delete it even with backups still inside — don't remove that flag, or destroy will fail on a non-empty bucket.
