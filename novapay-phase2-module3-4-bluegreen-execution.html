Core Concepts

Why Blue/Green for Payment-Critical Services
TYPE Concept APPLIES TO payment-service · auth-service NOT FOR kyc-service · webhook-service
The Problem
In a standard Kubernetes rolling update, old and new pods serve traffic simultaneously during the transition period. For stateless services with no cross-request coupling, this is fine. But for services where requests are correlated across versions — authentication tokens issued by v1 consumed by v2 — version mixing causes failures. NovaPay's March incident was exactly this: POST /auth (v1) issued a token in v1-format; POST /charge (v2) couldn't parse it. 40 minutes of outage. Two Tier-1 banking clients impacted.

Rollout Resource — What Argo Rollouts Manages

// WHY autoPromotionEnabled: false
Human must approve the promotion. For a payment service processing $2.1M/day, no automated tool should flip production traffic without a human reviewing the preview smoke test. This is the manual gate that prevents automated bad deploys from ever reaching customers.
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payment-service
  namespace: novapay-prod
spec:
  replicas: 3
  strategy:
    blueGreen:
      activeService: payment-service-active    # Receives production traffic
      previewService: payment-service-preview  # Receives zero real traffic
      autoPromotionEnabled: false               # Human must approve
      scaleDownDelaySeconds: 60                 # Keep Blue 60s after promotion
  template:
    spec:
      containers:
        - name: payment-service
          image: 390402549817.dkr.ecr.us-east-1.amazonaws.com/novapay-poc/charge:v1.0.0
          readinessProbe:
            httpGet:
              path: /health
              port: 3002
            initialDelaySeconds: 5
            periodSeconds: 5

build-v2-images.sh

Script 1 — Create v2.0.0 ECR Tags Without Rebuilding
TIME <30 seconds IDEMPOTENT Yes — safe to re-run REQUIRES v1.0.0 in ECR
Purpose
Blue/Green needs two distinct image versions. This script creates v2.0.0 by re-tagging the existing v1.0.0 images in ECR using the manifest copy API. No Docker daemon, no CodeBuild, no source code rebuild needed.

In a real CI/CD pipeline, v2.0.0 would be a new commit built by CodeBuild/GitHub Actions with a unique SHA-based tag (e.g., v2.1.3-abc123f). The re-tagging approach here is for the lab demo only. In production, every image tag maps to a unique build artifact — never re-tag.

How It Works
Run
bash build-v2-images.sh
// STEP-BY-STEP LOGIC 1. Verify v1.0.0 exists — calls aws ecr describe-images for each of the 4 services. Exits with error if any are missing.
2. Check if v2.0.0 already exists (idempotency) — if all v2.0.0 tags exist, prints "Nothing to do" and exits cleanly. Safe to run 100 times.
3. Copy manifests — for each missing v2.0.0: fetches the v1.0.0 manifest JSON + media type, then puts it as v2.0.0. No image layers re-uploaded — just metadata.
4. Verify all 8 tags — lists all image tags per repository. Expected: v1.0.0 and v2.0.0 for each of auth, charge, webhook, kyc.

Part F — Rollback

Instant Rollback — March Incident Prevention Proof
STEPS F.1 – F.5 TIME ~2 min PROVES FR-06 · Rollback <60s
The Scenario
A bad release is deployed. In March, this caused 40 minutes of downtime. With Blue/Green, the broken code NEVER reaches production traffic. Rollback takes 2–3 seconds.
F.1
F.1

Deploy a broken version

DELIBERATE FAILURE
// WHY nginx as the broken image
Using nginx as the image — it listens on port 80, but the readiness probe checks port 3002 /health. The probe will fail. Green pods will never become Ready. Production stays on v2.0.0 — zero customer impact.
kubectl argo rollouts set image payment-service \
  payment-service=public.ecr.aws/nginx/nginx:alpine \
  -n novapay-prod
F.2
F.2

Watch it fail SAFELY

OBSERVE
// THE KEY INSIGHT
Green pods enter CrashLoopBackOff (readiness probe failing). But the active Service selector NEVER changes. All production traffic continues on v2.0.0. Zero customer impact. This is exactly what didn't happen in March — the March deploy changed the selector.
kubectl argo rollouts get rollout payment-service -n novapay-prod
# You see:
#   Green: 3 pods, 0 Ready, CrashLoopBackOff
#   Active (v2.0.0): 3 pods, Running — STILL SERVING 100%

# Prove production is healthy:
kubectl exec -n novapay-prod deploy/auth-service -- \
  wget -qO- http://payment-service-active.novapay-prod.svc.cluster.local/health
# Returns: {"service":"charge","status":"ok",...} — working perfectly
F.3
F.3

ABORT — Instant rollback

2–3 SECONDS · FR-06 PROVEN
// THIS IS THE MOMENT
One command. Scales broken Green to 0. Production continues uninterrupted. This is the moment that would have prevented 40 minutes of downtime in March.
START=$(date +%s)
kubectl argo rollouts abort payment-service -n novapay-prod
END=$(date +%s)
echo "Rollback time: $((END - START)) seconds"
# Output: Rollback time: 2 seconds
// FR-06 PROVENRollback in 2–3 seconds. Requirement was <60s. The broken nginx image NEVER served a single production request.

Part G — Comparison

Rolling Update Version Mixing on kyc-service
STEPS G.1 – G.2 TIME ~1 min PROVES WHY payment needs Blue/Green
The Point
kyc-service uses a standard Kubernetes Deployment (rolling update). Watch both v1.0.0 and v2.0.0 serve traffic simultaneously during the update. For kyc-service this is acceptable. For payment-service this would be the March incident.
G.1 – G.2
kubectl set image deployment/kyc-service -n novapay-prod \
  kyc-service=390402549817.dkr.ecr.us-east-1.amazonaws.com/novapay-poc/kyc:v2.0.0

# IMMEDIATELY check:
kubectl get pods -n novapay-prod -l app=kyc-service \
  -o jsonpath='{range .items[*]}{.spec.containers[0].image}{"\n"}{end}'
# Output (during transition):
#   .../kyc:v1.0.0   ← old pod still serving
#   .../kyc:v1.0.0   ← old pod still serving
#   .../kyc:v2.0.0   ← new pod ALSO serving
#   .../kyc:v2.0.0   ← new pod ALSO serving

Version Mixing: kyc vs payment

  • Both v1.0.0 and v2.0.0 pods serve traffic simultaneously — Request 1 → v1.0.0, Request 2 → v2.0.0
  • For kyc-service (stateless, no cross-request coupling): this is acceptable
  • For payment-service: POST /auth (v1) issues token → POST /charge (v2) can't parse it → charge fails → THE MARCH INCIDENT
  • This is why payment-service needs Blue/Green and kyc-service can use rolling update

Production at Scale

Capacity Planning, Multi-AZ, PDB, Promotion Strategies
TYPE Production Engineering APPLIES TO Any Blue/Green at scale
Capacity Planning
// BLUE/GREEN REQUIRES 2× POD RESOURCES DURING TRANSITIONDuring the pause phase, both Blue (3 pods) and Green (3 pods) run simultaneously. For NovaPay's payment-service with 3 replicas × 512Mi memory = 1.5Gi extra during deploy.
ScaleReplicasMemory During DeployMitigation
Small (lab)3+1.5 GiKarpenter auto-provisions
Medium (prod)10+5 GiKarpenter + consolidation policy
Large (peak)50+25 GiPre-warm nodes, Spot for Green during preview
Multi-AZ Topology
// TOPOLOGY SPREADThe Rollout includes topologySpreadConstraints to distribute pods across availability zones. During Blue/Green transition, both sets maintain zone distribution.
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: payment-service
PDB During Rollout
// PodDisruptionBudget During Blue/Green
  • minAvailable: 2 ensures that node maintenance, spot interruptions, or Karpenter consolidation cannot evict pods below the minimum. During Blue/Green, this applies to BOTH Blue and Green pods independently.
  • Gotcha: If you have exactly 2 replicas with minAvailable: 2, node drain will be blocked entirely. Always use replicas ≥ minAvailable + 1.
Promotion Strategies
StrategyConfigUse Case
Manual gate (current)autoPromotionEnabled: falseHigh-risk services, compliance requirements
Auto with delayautoPromotionEnabled: true
autoPromotionSeconds: 300		Auto-promote after 5min if Green stays healthy
Analysis-drivenAnalysisTemplate with Prometheus metricsPromote only if error rate <0.1% after 10min
// PRODUCTION-GRADE ANALYSISTEMPLATEThis auto-aborts the rollout if the 5xx error rate exceeds 1% — fully automated March incident prevention.
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: payment-service-canary-check
spec:
  metrics:
    - name: error-rate
      interval: 60s
      count: 5
      successCondition: result[0] < 0.01
      provider:
        prometheus:
          address: https://aps-workspaces.us-east-1.amazonaws.com/workspaces/ws-xxx/
          query: |
            sum(rate(http_requests_total{service="payment-service",status=~"5.."}[2m]))
            /
            sum(rate(http_requests_total{service="payment-service"}[2m]))
