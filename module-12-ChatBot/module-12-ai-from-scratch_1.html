01

What a language model actually is.

// strip away the hype — it's a next-token predictor
Type Core concept Lab ref module-12-guided.sh
Core idea

Strip away the hype. A large language model (LLM) is a next-token predictor. You give it some text, and it predicts the most likely next chunk of text, then the next, then the next — one piece at a time, until it decides to stop. That's it.

"Mistral-7B" running in this lab is doing exactly that when it answers "What is a payment chargeback?" — it's generating one likely piece after another.

Everything else — answering questions, writing code, summarising documents — is that one trick applied to text that happens to look like a conversation.

Your phone's autocomplete is a tiny, basic language model. Type "I'll be there in" and it suggests "five minutes." Mistral-7B is the exact same idea — just with 7 billion learned numbers instead of a few thousand, trained on vastly more text. The mechanism is identical; the scale is not. When the model answers your support question, it's doing autocomplete — extremely good autocomplete, but autocomplete nonetheless.

02

Tokens, parameters, and weights.

// the two units everything is measured in
Type Core concept Why it matters Cost + size
Tokens

The model doesn't see words or letters. It sees tokens — pieces of words. "chargeback" might be two tokens: charge + back. A rough rule: 1 token ≈ ¾ of a word, or ~4 characters.

You saw real token counts in this lab's responses:

"usage": {
  "prompt_tokens": 14,      // your question was 14 tokens
  "completion_tokens": 34,  // the model generated 34 tokens of answer
  "total_tokens": 48
}
Why tokens matter You pay in compute time per token. Limits — the context window, max_tokens — are all measured in tokens. When you set max_tokens: 80, you're capping the answer at 80 tokens, not 80 words.
Parameters

"Mistral-7B" means the model has 7 billion parameters. A parameter (also called a weight) is a single number the model learned during training. Those 7 billion numbers, multiplied and added together in a specific structure, are what turn your input tokens into a prediction for the next token.

More parameters

  • Generally smarter and more capable
  • Bigger, slower, needs more memory
  • Costs more to run — bigger accelerator needed
  • Frontier models are 100B–1T+ parameters

7B — why this lab uses it

  • "Small" by today's standards
  • Fits on a single inf2.xlarge (1 Inferentia2 chip)
  • Fast enough for demo/learning purposes
  • Still capable enough for real support answers
The "weights" are the files the init container downloads in this lab — hf download aws-neuron/Mistral-7B-Instruct-…. That download, gigabytes of data, is the 7 billion numbers. The model is those numbers. There is no other secret. When you load the model, you're loading those numbers into the Neuron chip's memory so they can be used for matrix multiplication on each token.
03

Training vs inference.

// two completely different activities — this lab is 100% inference
Type Core concept Career impact High
The distinction

There are two completely different activities involving an LLM. Most people conflate them. Don't.

Training — NOT what you're doing

  • The slow, massively expensive process of learning those 7 billion numbers
  • Done once, by Mistral's creators, on huge GPU clusters over weeks
  • Requires millions of dollars of compute
  • Produces the model weights (the files you download)
  • You are NOT doing this in the lab — ever

Inference — what this lab does ✓

  • Using the already-trained weights to answer a question
  • Fast — milliseconds to seconds per request
  • Relatively cheap — a fraction of a cent per query
  • Happens every single time someone sends a chat message
  • This lab is 100% inference, start to finish
Most production "AI engineering" is inference — serving, scaling, securing, and optimising a model that someone else trained. That's the cloud-architect-adjacent skill. You don't need to understand backpropagation or gradient descent to build production AI systems. What you need to understand is how to run the model reliably, cheaply, and securely inside your own infrastructure — which is exactly what this module teaches.
04

Knowledge limits & hallucination.

// what the model knows, what it doesn't, and why it lies confidently
Type Critical Fix RAG (next module)
Knowledge cutoff

The model only knows what was in its training data, frozen at the moment training finished. It has no access to the internet, no access to your systems, and no awareness of anything that happened after its training cutoff.

What it answers well

  • General knowledge questions — "what is a chargeback?" "what is KYC?" — because the public internet (its training data) is full of that
  • Coding questions, writing, summarisation of text you paste in
  • Anything well-represented in public text before the training cutoff

What it cannot know

  • Anything about your company — NovaPay's policies, prices, account rules
  • Live data — current balances, transaction history, today's exchange rate
  • Events after its training cutoff
  • Private/internal documents it has never seen
When this lab asked "What is NovaPay's exact refund policy?", the real Mistral-7B replied: "I don't have real-time data or specific account information… general information about how refund policies might work for a company like NovaPay based on typical industry practices." — That's the honest answer. The problem is it won't always be that honest.
Hallucination

The model produces a confident, fluent, wrong answer

  • When pushed for specifics it doesn't have, the model often hallucinates — makes something up that sounds completely plausible
  • Remember: it's a next-token predictor. "Plausible-sounding text" is exactly what it optimises for, whether or not it's true
  • A bigger model doesn't fix this — a larger model will hallucinate more convincingly
  • The fix is giving the model your data at question time — not hoping it somehow already knows

There are two engineering approaches to fix hallucination:

RAG — what the next module covers ✓

  • Retrieval-Augmented Generation
  • Before answering, search your documents, find the relevant passages, paste them into the prompt
  • The model then answers from those passages
  • ~90% of enterprise chatbots work this way
  • Works for live data — fetch at query time

Fine-tuning — less common, less flexible

  • Adjust the model's weights on your data
  • Heavier — requires GPU time and ML expertise
  • Still can't know live data (a current balance, today's rate)
  • Used for teaching the model a style or format, not facts
  • Not covered in this module
The gap is deliberate This lab gives you the engine. It does not give the engine NovaPay's knowledge. Seeing that gap — asking about NovaPay's refund policy and getting a generic answer — is the lesson that motivates the next module (RAG).
05

Context window, prompts & the dials.

// the four knobs you control every time you call the model
Type Core concept Lab ref demo.sh ask()
Context window

The model can only "look at" a limited amount of text at once. In this lab, --max-model-len 2048 means the model's window is 2048 tokens total (your prompt + its answer combined). That's its entire working memory for a single request.

Go over 2048 tokens and the oldest text falls out of view — the model effectively "forgets" the start of a very long conversation. This is why:

Why context window size matters in production
  • Long documents must be chunked before being passed to the model — you can't paste a 100-page policy document into a 2048-token window
  • A chatbot "forgets" the start of a very long conversation when the window fills up
  • RAG depends on chunking — the retrieved passages must fit inside the window alongside the question
  • 2048 is small — chosen to fit our lab hardware. Production Mistral models support 32k tokens. Claude and GPT-4 support 128k–200k tokens.
Prompts & dials

Every request to the model is a structured JSON payload. Look at the real request this lab sends:

{
  "model": "/models/mistral-7b-v0.3",
  "messages": [
    {
      "role": "system",
      "content": "You are NovaPay's support assistant. Answer briefly."
    },
    {
      "role": "user",
      "content": "What is a payment chargeback?"
    }
  ],
  "max_tokens": 80,
  "temperature": 0.2
}
FieldWhat it doesLab value & why
system message Instructions that set the model's behaviour, persona, and scope. The user never sees it — it shapes every single answer silently. This is your biggest lever. "Prompt engineering" is mostly about getting this right. "You are NovaPay's support assistant. Answer briefly." — sets persona and tone before the user types anything
user message The actual question from the person chatting. What they typed. "What is a payment chargeback?" — the real question
max_tokens Hard cap on answer length in tokens. Answers cut off at the limit show finish_reason: "length" instead of "stop". Setting this too low produces truncated answers; too high costs more compute. 80 tokens — short for support answers. If you see truncated answers, increase this.
temperature The creativity / randomness dial, from 0 to 2. Low (0.2) = focused, consistent, repeatable — same question, same answer. High (1.5+) = more varied and creative, but more likely to wander or make things up. For support bots: keep it low. 0.2 — focused and consistent, right for a support assistant answering factual questions
06

Why it needs special hardware — and the three-layer stack.

// accelerator → vLLM → openai api → open webui
Type Architecture Node inf2.xlarge
Accelerator

Predicting the next token means multiplying huge grids of numbers — the 7 billion weights — together billions of times per token. A regular CPU does matrix multiplication sequentially. That's far too slow for real-time responses.

Accelerators — GPUs, or AWS's own Inferentia/Trainium chips — are purpose-built to do this matrix math in massive parallel batches. Without one, a 7B model takes minutes to generate a single response. With one, it takes milliseconds.

This lab uses an inf2.xlarge — one AWS Inferentia2 chip with 2 Neuron cores. That core count is why you see these flags in the vLLM deployment:

# Split the model across both cores — each core holds half the weights
--tensor-parallel-size 2
NEURON_RT_NUM_CORES=2

"Tensor parallelism" means slicing the 7B weight matrix in half and distributing it across both Neuron cores, which then collaborate on each token prediction. Bigger models need more cores (split across more chips). Bigger chips like trn1.32xlarge or inf2.48xlarge support much larger models.

Taint & toleration

The Neuron node is expensive — $0.76/hr. You don't want CoreDNS, your chat UI, or any system pod landing on it and wasting that compute. Kubernetes taints solve this.

Real-world analogy before the Kubernetes version: Imagine you have a mixed cluster with both Windows nodes and Linux nodes. You have a .NET application that can only run on Windows — it won't even start on a Linux node. You need a way to tell Kubernetes "only schedule this pod on Windows nodes" and "keep everything else off Windows nodes."

You taint every Windows node: os=windows:NoSchedule. This means: "nothing lands here unless it explicitly says it can tolerate this." Then you add a matching toleration to your .NET pod: "I can tolerate os=windows." Only the .NET pod gets scheduled on Windows nodes. Everything else — your Python microservices, your databases, your monitoring — stays on Linux nodes.

Now in this lab: the inf2.xlarge Neuron node is tainted aws.amazon.com/neuron=true:NO_SCHEDULE. Only the vLLM pod (the Mistral model pod) has the matching toleration. CoreDNS, Open WebUI, your system pods — all stay off the expensive accelerator. You pay $0.76/hr for exactly one thing: running the model. 
# The taint on the inf2.xlarge node (set in main.tf node group)
taint {
  key    = "aws.amazon.com/neuron"
  value  = "true"
  effect = "NO_SCHEDULE"     # nothing lands here unless it tolerates this
}

# The toleration in the vLLM pod spec — only this pod can land on the Neuron node
tolerations:
  - key: "aws.amazon.com/neuron"
    value: "true"
    effect: "NoSchedule"
vLLM

You don't write your own program to load and run the model. vLLM is an open-source inference server that does it for you: point it at the model weights, it loads them onto the Neuron cores and exposes an HTTP API so anything can send prompts and get answers.

Why vLLM is the industry standard for self-hosted LLMs
  • Efficient — PagedAttention: a memory management technique that lets vLLM serve many simultaneous requests on one accelerator by intelligently batching them. Without it, each request would hog the entire GPU/chip until done. This is what makes self-hosting affordable.
  • OpenAI-compatible API: vLLM exposes the exact same HTTP endpoints that OpenAI uses. Any tool that can call OpenAI can call your self-hosted model by changing one URL. No code changes needed.
  • Neuron support: vLLM has built-in support for AWS Inferentia/Trainium chips, which is why this lab uses it rather than a simpler alternative.
OpenAI API standard

vLLM exposes the same HTTP endpoints OpenAI uses — this is a de-facto industry standard:

EndpointWhat it doesUsed in lab
GET /v1/modelsLists the model(s) currently served — confirms Mistral is loaded and readymodule-12-demo.sh Step B.2
POST /v1/chat/completionsSend a conversation (system + user messages), get the model's next replyEvery chat message, module-12-demo.sh ask()

This standard means any client — Open WebUI, curl, Python scripts, LangChain, LlamaIndex, your own app — can talk to your self-hosted Mistral by setting one environment variable:

# How Open WebUI connects to vLLM — one variable, no code changes
OPENAI_API_BASE_URL=http://mistral.vllm:8080/v1

The model (vLLM) and the UI (Open WebUI) are completely decoupled. Swap the model for Llama or Phi without touching the UI. Swap the UI without touching the model. That's intentional architecture.

07

Why a bank self-hosts instead of calling OpenAI.

// data residency — the compliance argument in plain terms
Type Business + compliance Regulation PCI-DSS · GDPR · FCA
The problem

The easy path is to call a public LLM API — OpenAI, Anthropic, Gemini. One API key, done. The problem for a bank is what goes inside the prompt.

Customer prompts contain regulated data

  • Account numbers, sort codes, IBAN numbers
  • Transaction amounts and histories
  • Sometimes card data — PAN, expiry, CVV fragments
  • Personal identifiable information — names, addresses, DOBs

Sending any of that to a public API means the data crosses your network boundary and lands on a server you don't control. That's a:

Regulatory violations triggered by sending prompts to a public LLM API
  • PCI-DSS violation — cardholder data cannot leave your controlled environment to a non-PCI-certified third party
  • GDPR violation — personal data being processed by a third party without a Data Processing Agreement in place
  • FCA operational resilience rules — outsourcing critical functions (customer support decisioning) to a third party without proper risk management and contracts
  • Internal security policy — most banks explicitly prohibit sending customer data to external AI services, full stop
The solution

In this lab, the model is a ClusterIP service — internal only, no public endpoint, no internet access. The prompt goes from the browser UI to the model and back, entirely inside your VPC, on hardware in your own AWS account. It never leaves.

FIG 3 — Self-hosted: data stays inside. Public API: data crosses your boundary. For a bank, there is only one option.

That's the whole reason to self-host, and it's the one thing you never compromise on. Glossary
LLMLarge Language Model. A next-token predictor trained on massive amounts of text. Mistral-7B is an LLM.
TokenA piece of a word — the unit the model reads and generates. ~¾ of a word, or ~4 characters. All limits and costs are measured in tokens.
Parameter / weightOne of the billions of numbers the model learned during training. The model file is these numbers.

TrainingThe one-time, expensive process of learning the weights from huge amounts of text. Done by Mistral's team, not you.
InferenceUsing the already-trained weights to answer a question. What this lab does — every chat message is inference.
Knowledge cutoffThe date training data stopped. The model knows nothing after this date and nothing about your internal systems.
HallucinationWhen the model confidently produces a fluent, wrong answer about something it doesn't actually know.
RAGRetrieval-Augmented Generation. Searching your documents for relevant passages and injecting them into the prompt before asking the model. Fixes hallucination for company-specific knowledge.
Context windowThe maximum number of tokens the model can consider in one request — prompt + answer combined. 2048 tokens in this lab.
System messageThe hidden instructions that set the model's persona and behaviour before the user types anything. Your biggest lever.
TemperatureRandomness dial (0–2). Low = focused and consistent. High = creative but more likely to hallucinate. Support bots: keep it low (0.2).
max_tokensHard cap on answer length in tokens. Prevents runaway long responses and caps compute cost per query.
AcceleratorSpecialist chip (GPU, AWS Inferentia, AWS Trainium) that does the matrix math fast. Without one, a 7B model is unusably slow.
AWS Inferentia2AWS's custom inference chip. The inf2.xlarge has one Inferentia2 chip with 2 Neuron cores.
Neuron coreA compute unit inside an Inferentia2 chip. The inf2.xlarge has 2 cores. The model is split across both (tensor parallelism).
Tensor parallelismSplitting the model's weight matrix across multiple cores so they work in parallel. Required when the model is too big for one core.
Neuron device pluginA Kubernetes DaemonSet that tells the scheduler that Neuron cores exist on this node and can be requested by pods.
TaintA Kubernetes node property that says "nothing lands here unless it explicitly tolerates this." Used here to protect the expensive Neuron node.

PagedAttentionvLLM's memory management technique that allows multiple concurrent requests to share the accelerator by batching them intelligently.

ClusterIPKubernetes service type. Internal only — no public endpoint, no internet access. Used for the vLLM service to enforce data residency.
Open WebUIThe browser-based chat UI in this lab. It's just a client of the vLLM API — no intelligence of its own.
Data residencyThe requirement that data stays inside a defined geographic or network boundary. For NovaPay: customer prompts must stay inside the VPC. Self-hosting enforces this.
Summary

Module 12 — what you now understand

  • An LLM is a next-token predictor — it predicts the most likely next piece of text, one token at a time, until it stops. Everything else is this one trick at scale.
  • Tokens are the unit everything is measured in. Parameters/weights are the 7 billion numbers that do the predicting. The download is the model.
  • Training = learning the numbers (done by Mistral, not you). Inference = using the numbers to answer (this lab is 100% inference).
  • The model knows general knowledge but nothing about NovaPay. When pushed for specifics, it hallucinates — confidently producing wrong answers. The fix is RAG (next module).
  • The context window (2048 tokens here) is the model's total working memory per request — prompt + answer combined. Go over it and old context is forgotten.
  • The system message, temperature, and max_tokens are the three dials you control on every call. The system message is your biggest lever.
  • The inf2.xlarge Neuron node does the matrix math. The taint (+ .NET/Windows analogy → Neuron analogy) keeps non-model pods off the expensive node. vLLM runs the model and speaks the OpenAI API. Open WebUI is just a UI client.
  • A bank self-hosts because customer prompts contain regulated data. Sending them to a public API crosses the compliance boundary. ClusterIP service = internal only = data never leaves the VPC.
  • Next module: RAG — giving the model NovaPay's actual policies, so it answers from real data instead of hallucinating.

customer data inside your boundary.

Self-hosting an LLM is not about saving money on API calls. It's about owning the data path entirely — so no prompt ever crosses a boundary you can't control.
